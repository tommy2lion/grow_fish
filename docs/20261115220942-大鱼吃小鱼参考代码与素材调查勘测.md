# 大鱼吃小鱼参考代码与素材调查勘测

> 文档性质：课程设计前期调查与勘测
> 调查对象：GitHub 参考仓库 `lgc0208/BigFishEatSmallFish`、原指导书配图、公开素材源
> 调查日期：2026-11-15
> 结论摘要：参考代码只是一个可运行的小型 demo，与课设基本要求差距较大，**建议重写**；仅借鉴玩法与视觉思路，素材优先使用 CC0 资源或 EasyX 绘制。

## 1. 调查背景与目标

课程设计选题为题目 2「大鱼吃小鱼」（按学号尾号偶数分配）。为评估实现路线，对以下内容进行调查：

1. 从 GitHub 下载的参考仓库 `https://github.com/lgc0208/BigFishEatSmallFish` 的代码完成度与质量；
2. 参考仓库及原指导书中的图片素材可用性与授权情况；
3. 公开可用的鱼类素材来源；
4. 判断应在参考代码上改造，还是重写。

调查方法：文件清单与行数统计、图片尺寸检测、逐文件静态阅读、对照课设需求逐项核查、公开素材源检索。

参考仓库本地位置：`refer/BigFishEatSmallFish/`（`refer/` 已在 `.gitignore` 中忽略，不会进入版本库）。

### 3.2 工程规范差距

- **未使用链表**：题目明确要求所有鱼用链表实现存储与增删，参考代码使用固定数组，数据结构直接不符合要求。
- **模块化不足**：全局变量和所有函数实现都写在 `Functions.h` 中，`main` 之外没有清晰的模块划分，不符合“高内聚低耦合、模块化程序设计”的要求。
- **全局变量过多**：`ScreenWidth`、`ScreenHeight`、`IMAGE Fish[3]`、`player` 相关状态等均为全局；题目要求尽可能少用全局变量。
- **无模块调用图基础**：现有结构难以支撑报告中要求的模块划分与函数原型清单。
- **编码问题**：源码为 GBK 编码，在 VS2022/UTF-8 环境下注释显示为乱码，直接并入需要转码。

## 4. 代码质量勘测

主要问题（按影响排序）：

1. **随机移动逻辑错误**：`movefish()` 中 `fish1->y += (rand() & 21) - 10;` 使用按位与，取值并非均匀的 −10~10，属于逻辑 bug，应为 `% 21`。
2. **透明贴图实现会破坏素材**：`changeImage()` 直接修改 `imagePut` 的像素缓冲区（把背景像素改成黑色），源图被永久改变；连续绘制时素材会逐渐失真。
3. **硬编码尺寸**：`changeImage2()` 固定按 `100×100` 处理，而实际图片尺寸各不相同（如 650×357、1200×1200），缩放/掩码逻辑与素材不匹配。
4. **碰撞检测粗糙**：`iftouch()` 只比较两个对象左上角坐标差是否小于 `N`（50），没有考虑鱼的宽高、玩家体型和真实包围盒，碰撞判定不准确。
5. **暂停实现不合理**：主循环中按 P 后执行 `ret = _getwch();`，会阻塞等待一个宽字符，既不是暂停菜单，也不符合正常的暂停/继续交互。
6. **阻塞式开始/结束**：`getchar()` 需要按 Enter 才能继续；结束页用 `while (_kbhit())` 清空键盘缓冲区，交互体验差。
7. **宽高变量命名颠倒**：`ScreenWidth=480`、`ScreenHeight=640`，但 `initgraph(ScreenHeight, ScreenWidth)` 实际得到 640×480 窗口，变量名与实际含义相反，易错。
8. **音乐路径依赖工作目录**：`mciSendString(L"open music.mp3", ...)` 使用相对路径，从不同目录启动会失败；且未检查返回值。
9. **缺少双缓冲**：直接每帧重绘，鱼多或窗口刷新时容易闪烁。
10. **无计时/帧率控制抽象**：仅 `Sleep(40)`，没有统一的时间步长、倒计时和游戏状态管理。
11. **不必要的依赖**：`#include <iostream>`、`using namespace std;` 在纯 EasyX 项目中无实际用途。

结论：参考代码的“可运行”不等于“可改造”。其主循环、数据结构和绘制方式都需要重做，改造工作量大于重写。

| 来源 | 内容 | 授权 | 备注 |
| --- | --- | --- | --- |

| [OpenGameArt 8x8 Sea Creatures](https://opengameart.org/content/8x8-sea-creatures) | 10 个 8×8 海洋生物像素图 | CC0 | 适合极小分辨率或占位 |

替代方案：**直接用 EasyX 绘制几何图形**（椭圆、圆、多边形、扇形）表示鱼、玩家、炸弹、闹钟。优点是零版权风险、无透明贴图问题、便于控制碰撞盒；缺点是不够美观，但课设评分重点是逻辑、模块化、链表和文件读写，不是美术。

如果使用图片，建议：

- 统一转成透明 PNG，放入 `assets/`，按 `fish_small.png`、`fish_big.png`、`player.png` 等命名；
- 使用 EasyX 的 `loadimage` + `TransparentBlt` 或正确的掩码方式，避免参考代码“篡改源缓冲区”的做法；
- 图片尺寸统一为 2 的幂或统一基准尺寸，便于碰撞盒和缩放。

| 内容 | 是否可复用 | 说明 |

| 代码本身 | 不建议复用 | 改造量大于重写，且存在雷同风险 |

## 7. 建议方案

### 7.1 结论

**重写**。参考仓库仅用于理解玩法、观察视觉风格和临时占位；不直接复制代码。

理由：

1. 参考代码未实现课设的大部分基本功能，补全成本高；
2. 数据结构（固定数组）与课设硬性要求（链表）冲突，需要重做；
3. 代码架构、绘制、碰撞、输入均需重写；
4. 课设要求独立完成，直接复用他人代码存在雷同/不及格风险；
5. 从零搭建模块化框架反而更清晰、可控，便于撰写设计报告和模块调用图。

### 7.2 模块划分

```text
main.cpp        初始化、登录、主菜单、主循环
game.cpp/h      游戏状态、倒计时、目标分、胜负判定
fish.cpp/h      Fish 链表：生成、插入、删除、移动、绘制
player.cpp/h    玩家移动、成长、生命、碰撞
render.cpp/h    背景、精灵、文字、三区布局、双缓冲
input.cpp/h     键盘、鼠标
data.cpp/h      文件存档、最高分、排行榜
ui.cpp/h        登录、按钮、暂停、结束界面
```

### 7.3 核心数据结构（建议）

```c
typedef enum { FISH_SMALL, FISH_BIG, FISH_BOMB, FISH_CLOCK } FishType;

typedef struct Fish {
    FishType type;
    float x, y, vx, vy;
    int size, score;
    struct Fish *next;
} Fish;

typedef struct {
    Fish *head, *tail;
    int count;
} FishList;

typedef struct {
    char name[32];
    float x, y;
    int size, lives, score;
    bool alive;
} Player;
```

说明：EasyX 只能在 C++ 模式下编译，因此源码使用 `.cpp` 扩展名，但代码风格保持 C 语言的过程式写法（结构体 + 函数 + 链表），符合课程要求。

### 7.4 开发里程碑

1. 可编译框架：窗口、登录界面、主界面三区（游戏区/按钮区/信息区）、按钮响应；
2. 鱼链表：生成、左右两侧游入、移动、出界删除/重生；
3. 玩家移动、吃鱼加分、体型成长、撞大鱼扣血、生命值显示；
4. 倒计时、目标分、闹钟加时间、炸弹减时间、胜负判定；
5. 暂停/结束/重新开始、文件存档、最高分/排行榜；
6. 扩展功能：鼠标控制、生命模式、音效、动画与视觉优化。

### 7.5 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 课设雷同/抄袭风险 | 从零重写，不复制参考代码；报告中说明设计过程 |
| 链表实现不完整 | 单独封装 `FishList`，实现插入、删除、遍历、销毁 |
| 文件读写缺失 | 早做存档设计（玩家名、分数、时间、最高分） |
| 倒计时/状态管理混乱 | 统一 `GameState` 状态机，明确 `Menu/Playing/Paused/Over` |
| 图片透明/闪烁 | 使用透明 PNG 或 EasyX 绘图；启用双缓冲 |
| Unicode/MBCS 不一致 | 统一字符集设置（建议多字节），或统一使用 `_T()` |
| 时间不足 | 优先完成基本功能，再做扩展；每阶段保持可编译 |
